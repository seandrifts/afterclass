# 後台規格

版本 v2.0 / 2026-07-28
搭配 [`PLAN.md`](./PLAN.md) 閱讀。主力機制為儲值金（對外稱「回饋點數」）

---

## 0. 核心原則

**所有數字都在後台改，改完立即生效，不用重新部署。**

程式碼裡不出現任何寫死的獎項、機率、金額、天數。工程師只寫「讀設定 → 執行邏輯」，數值全部從 `settings` 與 `prizes` 兩張表來。

四個必守規則：

1. **獎項只能停用，不能刪除**。刪除鍵實際執行 `is_active = false`
2. **改設定不影響已發出的券**。券在中獎當下就快照了內容（`PLAN.md` §6.0）
3. **改設定不追溯既有餘額**。把到期天數從 90 改成 60，只影響之後的異動，已經算好的 `balance_expires_at` 不動。追溯縮短客人的到期日是會被投訴的
4. **所有異動留 log**。誰在什麼時候把什麼從 A 改成 B，全部記錄。餘額的人工調整必填原因

## 1. 登入與權限

| 角色 | 進入方式 | 權限 |
|---|---|---|
| 老闆 owner | `/admin`，LINE 登入 + email 白名單 | 全部 |
| 店員 staff | `/staff`，4 位 PIN | 只能核銷券、發動態 QR、看今日統計 |

老闆的 email 白名單放環境變數 `ADMIN_EMAILS`，middleware 擋。店員 PIN 用 bcrypt hash 存 DB。

店員**看不到**成本、機率、報表、會員名單。這些是商業機密，也避免店員知道機率後幫親友挑時機。

## 2. 儀表板 `/admin`

進來第一眼要能回答「今天這活動花了我多少錢、帶來多少人」。

### 2.1 頂部四張卡

```
┌──────────────┬──────────────┬──────────────┬──────────────┐
│ 今日發放      │ 今日抽獎      │ 今日折抵      │ 今日成本      │
│    78 張      │  52 次 (67%)  │  NT$ 186      │   NT$ 191    │
│  ▲ 較昨日 +6  │  ▲ +4         │  23 筆        │  佔營業額2.0% │
└──────────────┴──────────────┴──────────────┴──────────────┘
```

「今日成本」= 今日實際折抵金額 + 今日核銷的免單成本。這是真正花掉的錢，不是發出去的點數。

**掃碼率（抽獎 ÷ 發放）是最重要的單一指標。**低於 50% 代表告示不清楚或 QR 不好掃，這時候調機率沒有意義，要先修這個。

### 2.2 本月概況

| 指標 | 數值 | 說明 |
|---|---|---|
| 累計成本 | NT$ 5,180 / 上限 9,000 | 進度條，接近上限變紅 |
| 新加入會員 | 142 人 | |
| 回訪客（本月來 2 次以上） | 58 人 (41%) | 活動有沒有效就看這個 |
| 平均回訪間隔 | 8.2 天 | 跟活動前比較 |
| 點數折抵率 | 78% | 已折抵 ÷ 已發放，影響實際成本 |
| **流通中點數（負債）** | **NT$ 3,420** | 客人手上還沒用的餘額總和 |
| 本月到期歸零 | NT$ 240 | 沉睡客自動出清的部分 |
| 30 天內即將到期 | NT$ 890 / 47 人 | 推播名單就從這裡來 |

**「流通中點數」是你的帳面負債。**這個數字會在活動初期一路上升，大約兩到三個月後趨於穩定（新發放 ≈ 折抵 + 到期）。如果它一直線上升沒有趨緩，代表金額太小客人懶得用，該調高級距或降低折抵門檻。

### 2.3 圖表

- 近 30 天每日發放/抽獎/折抵折線圖
- **點數流通量堆疊圖**（新發放 vs 已折抵 vs 已到期），看負債有沒有趨於穩定
- 獎項中獎分佈長條圖（實際 vs 設定機率，偏差過大代表演算法有問題）
- 時段分佈（幾點發最多，用來安排店員）

### 2.4 異常告警區

紅框顯示需要處理的事：

- 成本接近上限
- **餘額一致性檢查失敗**（`PLAN.md` §6.6 回傳非 0 列，代表有人繞過 ledger 動了餘額，最高優先）
- **流通中點數連續 3 個月上升未趨緩**
- 某獎項庫存快用完
- 某店員發放數異常（與來客數落差 > 20%）
- **某店員折抵金額異常**（單日折抵遠高於其他店員）
- 可用序號剩不到 50 張（該啟用下一批了）
- 實際中獎分佈與設定機率偏差 > 5%

**用權重不用百分比輸入。**你輸入整數權重，系統即時換算百分比。這樣改一個獎項不用手動調整其他項讓總和湊到 100，也避免浮點誤差。

**儲值金與免單的成本邏輯不同。**儲值金的成本 = 面額全額（折抵時直接減收入）；免單的成本 = 食材成本（150 元的餐你實際只損失 57 元）。之後如果加回實物券，成本同樣是食材成本而非售價。

### 3.2 即時成本試算（這是後台最有價值的功能）

列表下方常駐一塊面板，**你每改一個權重就立刻重算**，不用存檔：

```
┌─────────────────────────────────────────────────┐
│  成本試算                    基準：客單 120 / 日客 80 │
│                                                  │
│  平均抽到金額      NT$ 3.32 / 次                  │
│                                                  │
│  名目期望成本      NT$ 3.49 / 客                  │
│  ├ 核銷率修正後    NT$ 2.81 / 客   (佔客單 2.3%)  │
│  │                                               │
│  預估每日成本      NT$ 225                        │
│  預估每月成本      NT$ 6,740                      │
│                                      上限 9,000  │
│  [███████████████░░░░░] 75%                      │
│                                                  │
│  ⚠ 回饋金 3 元 佔總成本 21%                        │
└─────────────────────────────────────────────────┘
```

核銷率可以用兩種來源，切換選擇：

- **預估值**：儲值金 80%、免單 90%（手動可調）
- **實際值**：系統從歷史資料算出真實折抵率（累積 200 筆以上才夠準）

上線兩週後切到實際值，數字會準很多。

**儲值金的核銷率算法跟券不同**。券是「幾張被用掉」，儲值金是「發出去的總金額有幾成被折抵掉」：

```
實際折抵率 = 累計 spend 金額 ÷ 累計 earn 金額
```

初期這個數字會偏低（因為大家還在累積還沒開始用），至少要跑滿一個到期週期（90 天）才有參考價值。

底部的智慧提示會抓出成本結構問題，例如某個獎項吃掉過半成本、或大獎機率高到不合理。

```

選「儲值金」時，成本欄位自動鎖定等於入帳金額並顯示唯讀，避免填錯導致報表失真。其他類型才需要手動填成本。

**驗證規則：**

- 權重必須 ≥ 0 的整數。設 0 等於暫時不會抽到但保留設定
- 至少要有一個啟用且權重 > 0 的獎項，否則不能存（會讓抽獎爆掉）
- 成本不可為負
- **儲值金的入帳金額必須 ≥ 1 的整數**（不做小數，避免四捨五入誤差累積）
- 免單類型必須填折抵上限，否則不能存
- 現金券的門檻不可小於折抵金額（滿 50 折 100 是虧的）

**入帳金額超過單次折抵上限只跳警告，不擋。**例如「回饋金 50 元」搭配「單次折抵上限 30 元」：

```
ℹ 此獎項 50 元超過單次折抵上限 30 元，客人需分 2 次來店用完。
   這會增加回訪次數，是可接受的設計，但請確認條款有寫清楚單次上限。
```

餘額是一個池子不是一張券，用不完會留著，沒有浪費問題。分兩次用完反而多帶來一次來店。所以這不該是錯誤，只需要提醒你確認條款有寫。

### 3.5 危險操作的二次確認

改動如果讓每月預估成本上升超過 30%，跳確認框：

```
⚠ 這次調整會讓每月預估成本從 6,740 增加到 10,900（+62%）
   已超過你設定的月上限 9,000

   [ 取消 ]  [ 我知道，確認修改 ]
```

### 3.6 異動紀錄

頁面底部顯示最近 20 筆修改，誰、何時、把什麼從 A 改成 B。爭議時這是證據，也防止有人偷改機率。

### 5.2 人工調整餘額

處理客訴用。**必填原因**，且一律留 audit log。

```
會員         [陳小明 (LINE)          ] 搜尋
目前餘額     47 元

調整         (•) 增加  ( ) 扣除
金額         [ 30 ] 元
原因         [店員誤扣，補回          ]  ← 必填

調整後餘額   77 元

[ 確認調整 ]
```

**扣除時的保護**：不可扣到負數，餘額不足時直接擋下並顯示目前餘額。

**單次調整上限**建議設 500 元，超過需要二次確認。這是防止手滑多打一個零。

## 6. 會員 `/admin/members`

| 會員 | 來源 | 抽獎次數 | 累計獲得 | 累計折抵 | 目前餘額 | 到期日 | 最後來店 | 沉睡天數 |
|---|---|---|---|---|---|---|---|---|
| 陳小明 | LINE | 14 | 52 | 35 | 17 | 11/03 | 08/05 | 2 |
| 王大華 | Email | 3 | 20 | 0 | 0 | 已到期 | 07/30 | 8 |

**分群匯出 CSV：**

- **7 天內餘額到期且餘額 > 0**（推播優先名單）
- 沉睡客（超過 30 天沒來）且仍有餘額
- 高頻客（本月來 4 次以上）
- 累計獲得高但折抵率低的人（有餘額卻不來用，值得單獨推播）

這些名單是活動真正的產出。餘額即將到期的名單拿去 LINE 推播，效果遠比抽獎本身好。

單一會員頁顯示完整流水帳與消費軌跡，也可以封鎖（`is_blocked`）處理惡意刷點數的人。封鎖後無法折抵也無法再抽獎，但餘額保留。

折抵筆數        31 筆
平均每筆        NT$ 20.6      ✓ 正常（上限 30）

超過 ±20% 會標紅並在儀表板告警
```

**折抵是有現金價值的操作，比發序號更需要盯。**要看的異常訊號：

- 某店員的平均折抵金額明顯高於其他人（可能一律按「全部」而不問客人）
- 某店員在非尖峰時段有大量折抵（可能幫親友刷）
- 同一個會員帳號被同一位店員高頻折抵

單一店員頁可以看該店員的完整折抵紀錄，逐筆對照時間與金額。

如果都是家人顧店，這頁可以先不用。有請外人時再啟用。

## 8. 報表 `/admin/reports`

| 報表 | 內容 |
|---|---|
| **點數流量表** | 每日/週/月的 發放 / 折抵 / 到期 三個數字，看負債有沒有趨於穩定 |
| **負債表** | 流通中點數總額、帳齡分佈（0-30 / 31-60 / 61-90 天），給會計用 |
| 成本報表 | 依日/週/月，發放面額 vs 實際折抵金額，可匯出 CSV 給會計 |
| 獎項分析 | 每個獎項的中獎數、實際成本佔比 |
| 折抵率分析 | 累計折抵 ÷ 累計發放，回頭餵給 §3.2 的成本試算 |
| 回訪分析 | 活動前後的回訪間隔對比 |
| 時段分析 | 發放與折抵的時段分佈 |

**成本報表要區分三個數字，這是最容易搞混的地方：**

| 數字 | 定義 | 用途 |
|---|---|---|
| **已發放** | 抽獎入帳的點數總額 | 評估活動規模 |
| **流通中（負債）** | 客人手上還沒用的餘額 | 帳務上的潛在負債 |
| **實際成本** | 真正被折抵掉的金額 + 已核銷免單的食材成本 | **跟會計對帳看這個** |

三者關係：

```
已發放 = 已折抵 + 流通中 + 已到期歸零
```

活動初期「流通中」會一路上升，這是正常的累積期。大約兩到三個月後（跑滿一個到期週期）會趨於穩定，此時每月新發放 ≈ 每月折抵 + 每月到期。

**如果三個月後流通中還在直線上升**，代表客人不來用，可能是金額太小沒動機、或折抵流程太麻煩。這時候該調高級距或簡化店員操作，不是加碼獎項。

## 9. 設定 `/admin/settings`

### 9.1 品牌

店名、Logo、主色。抽獎頁的視覺跟著這裡走。

### 9.2 活動總開關

```
活動狀態     (•) 進行中   ( ) 暫停

暫停時，客人掃 QR 會看到：
[ 活動暫停中，造成不便敬請見諒 ]

活動期間     [2026-08-01] 到 [        ]   留空 = 無限期
```

**一鍵暫停是必要的煞車。**成本失控、獎品缺貨、系統出問題時要能立刻停。

暫停時**已累積的點數仍然可以折抵**，只是不能再抽新的。這符合消保法要求，也避免客人覺得錢被吞了。

### 9.3 儲值金規則

| 設定 | 預設 | 說明 |
|---|---|---|
| **餘額到期天數** | 90 | 滾動式，任何進出都往後順延 |
| **單次折抵上限** | 30 元 | 成本控制的第二道防線 |
| 折抵門檻 | 0 | 0 = 無門檻隨時可用 |
| 到期提醒提前天數 | 7 | 推播時機 |
| 顯示為點數 | 開 | 關掉就直接顯示「元」 |
| 點數倍率 | 10 | 1 元 = 10 點 |

**改動的追溯性規則（重要）：**

| 改什麼 | 影響範圍 |
|---|---|
| 到期天數 90 → 60 | **只影響之後的異動**，已算好的 `balance_expires_at` 不動 |
| 單次折抵上限 30 → 20 | 立即生效，下一筆折抵就套用 |
| 點數倍率 10 → 100 | 立即生效，只是顯示層 |

**縮短到期天數絕對不能追溯。**客人本來看到「11/03 到期」隔天變成「10/04 到期」，這是會被投訴到消保官的。改動時後台要明確顯示：

```
ℹ 到期天數從 90 改為 60。
   現有 142 位客人的到期日不受影響。
   下次異動時才會套用新規則。
```

### 9.4 活動規則

| 設定 | 預設 | 說明 |
|---|---|---|
| 實物券預設有效天數 | 21 | 獎項可個別覆寫 |
| 每次消費限用券數 | 1 | 防止一次用光一疊券 |
| 紙卡序號有效天數 | 90 | 印出來的卡多久後失效 |
| 動態 QR 存活秒數 | 60 | |
| 抽完到登入的領取時限 | 30 分鐘 | 超過未登入視為放棄 |
| 可否與其他優惠併用 | 否 | |

### 9.5 成本煞車

```
每月成本上限   [ 9000 ] 元    ( ) 不設限

達到上限時     (•) 只通知我
               ( ) 自動暫停活動

目前本月累計   NT$ 5,180 (58%)
```

我建議先選「只通知我」。自動暫停會讓客人在店裡掃碼卻抽不了，體驗很差，寧可你收到通知後自己決定怎麼處理。

**成本認列的時點**：以**實際折抵**計算，不是以發放計算。客人抽到 50 元但還沒來用，這時候還沒有成本。這樣算出來的數字才對得上你實際少收的現金。

流通中的點數另外列在儀表板當「負債」，兩個數字要分開看。

### 9.6 保底機制

```
[✓] 啟用保底
    同一會員連續 [ 20 ] 次抽到最低金額時，
    下一次排除最低級距
```

熟客一週來三次，連續抽到 1 元會覺得被耍。保底成本增加極小但體感差很多，建議開啟。

未登入的客人沒有保底，因為無法追蹤連續次數。這不影響什麼，會連抽 20 次的一定是登入過的熟客。

### 9.7 活動辦法

富文本編輯器，內容直接顯示在 `/rules` 頁。

**機率表由系統自動產生插入**，不要讓你手打。公平交易法要求公告機率必須真實，手打會有寫錯或忘記同步的風險。系統自動從 `prizes` 撈當前設定產生表格。

## 10. 技術實作要點

### 10.1 設定的讀取與快取

`settings` 是單列表，每次抽獎都要讀。用 Next.js `unstable_cache` 快取 60 秒，後台儲存時 `revalidateTag('settings')` 立即失效。

不要每次請求都打 DB，也不要快取太久導致「改完沒生效」的困惑。60 秒是平衡點，後台儲存後主動失效讓體感是即時的。

### 10.2 機率的即時試算放前端

`/admin/prizes` 的權重調整、百分比換算、成本試算，全部在前端即時算，不打 API。只有按儲存才寫 DB。這樣調整體驗才流暢。

但**抽獎本身的機率計算一定在後端**，兩者不衝突。前端算的只是給你看的預覽。

### 10.3 儲存時的原子性

獎項是一起儲存的（改一個權重會影響所有百分比），用 transaction 一次寫入全部異動，並在同一個 transaction 寫 `prize_change_log`。

### 10.4 餘額的人工調整一律走 RPC

後台調整餘額**不可以直接 `update users set balance = ...`**。必須呼叫跟店員端同一套 Postgres function，才能保證 ledger 一定被寫入。

繞過 ledger 直接改 balance，會讓 `PLAN.md` §6.6 的一致性檢查失敗，而且那筆錢查不出去向。這是整份規格裡最不能妥協的一條。

### 10.5 後台不需要即時

除了儀表板，後台其他頁面都可以用 Server Component 直接查 DB，不用做即時更新。儀表板加一個手動重整鍵就夠，不用 WebSocket。

### 10.6 手機可用

你很可能在店裡用手機看後台。至少儀表板、點數管理、序號啟用這三個要能在手機上操作。獎項編輯跟報表可以只做桌機版。
