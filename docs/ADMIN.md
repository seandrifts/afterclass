版本 v1.0 / 2026-07-28
搭配 [`PLAN.md`](./PLAN.md) 閱讀

## 0. 核心原則

**所有數字都在後台改，改完立即生效，不用重新部署。**

程式碼裡不出現任何寫死的獎項、機率、金額、天數。工程師只寫「讀設定 → 執行邏輯」，數值全部從 `settings` 與 `prizes` 兩張表來。

三個必守規則：

1. **獎項只能停用，不能刪除**。刪除鍵實際執行 `is_active = false`
2. **改設定不影響已發出的券**。券在中獎當下就快照了內容（`PLAN.md` §6.0）
3. **所有異動留 log**。誰在什麼時候把什麼從 A 改成 B，全部記錄

## 1. 登入與權限

| 角色 | 進入方式 | 權限 |
|---|---|---|
| 老闆 owner | `/admin`，LINE 登入 + email 白名單 | 全部 |
| 店員 staff | `/staff`，4 位 PIN | 只能核銷券、發動態 QR、看今日統計 |

老闆的 email 白名單放環境變數 `ADMIN_EMAILS`，middleware 擋。店員 PIN 用 bcrypt hash 存 DB。

店員**看不到**成本、機率、報表、會員名單。這些是商業機密，也避免店員知道機率後幫親友挑時機。

### 3.2 即時成本試算（這是後台最有價值的功能）

列表下方常駐一塊面板，**你每改一個權重就立刻重算**，不用存檔：

```
┌─────────────────────────────────────────────────┐
│  成本試算                    基準：客單 120 / 日客 80 │
│                                                  │
│  名目期望成本      NT$ 7.78 / 客                  │
│  ├ 核銷率修正後    NT$ 3.19 / 客   (佔客單 2.7%)  │
│  │                                               │
│  預估每日成本      NT$ 255                        │
│  預估每月成本      NT$ 7,650                      │
│                                     上限 10,000  │
│  [████████████████░░░░] 77%                      │
│                                                  │
│  ⚠ 折 10 元 佔總成本 51%，考慮降低權重或提高門檻    │
└─────────────────────────────────────────────────┘
```

核銷率可以用兩種來源，切換選擇：

- **預估值**：每個獎項手動填一個預估核銷率
- **實際值**：系統從歷史資料算出該獎項的真實核銷率（累積 200 張以上才夠準）

上線兩週後切到實際值，數字會準很多。

底部的智慧提示會抓出成本結構問題，例如某個獎項吃掉過半成本、或大獎機率高到不合理。

按「模擬 1000 次」，用目前設定跑一次蒙地卡羅：

折 50 元       6 次   0.60%   期望 0.70%   ✓

### 3.4 編輯獎項

```
獎項名稱      [滷蛋一顆                    ]
類型          ( ) 現金券  (•) 實物  ( ) 免單
感知價值      [ 12 ] 元      ← 顯示給客人看的
實際成本      [  5 ] 元      ← 只有你看得到，報表用

── 現金券專用（類型選現金券才出現）──
折抵金額      [    ] 元
使用門檻      [    ] 元      ← 滿多少才能用
折抵上限      [    ] 元      ← 免單專用

── 機率與庫存 ──
權重          [ 220 ]        目前機率 22.00%
庫存限制      (•) 無限  ( ) 總量 [    ]  ( ) 每日 [    ]

── 券設定 ──
有效天數      [ 21 ] 天      留空則用全域預設
專屬使用條件  [限內用，不可外帶            ]

── 外觀 ──
圖片          [ 上傳 ]

```

**驗證規則：**

- 權重必須 ≥ 0 的整數。設 0 等於暫時不會抽到但保留設定
- 至少要有一個啟用且權重 > 0 的獎項，否則不能存（會讓抽獎爆掉）
- 成本不可為負
- 免單類型必須填折抵上限，否則不能存
- 現金券的門檻不可小於折抵金額（滿 50 折 100 是虧的）

### 3.5 危險操作的二次確認

改動如果讓每月預估成本上升超過 30%，跳確認框：

```
⚠ 這次調整會讓每月預估成本從 7,650 增加到 12,400（+62%）
   已超過你設定的月上限 10,000

   [ 取消 ]  [ 我知道，確認修改 ]
```

### 3.6 異動紀錄

頁面底部顯示最近 20 筆修改，誰、何時、把什麼從 A 改成 B。爭議時這是證據，也防止有人偷改機率。

| 核銷碼 | 獎項 | 會員 | 狀態 | 到期日 | 核銷時間 | 核銷店員 | 操作 |
|---|---|---|---|---|---|---|---|

| 118273 | 折 50 元 | 王大華 | 未使用 | 08/25 | | | 作廢 / 延期 |

**手動操作：**

- **作廢**：客訴或誤發時用，要填原因
- **延期**：客人客訴「我人在外地趕不回來」，可以按延期給 7 天。這個小功能對客訴處理很有用
- **補發**：客人說核銷過程出錯，可以手動發一張券給他，要填原因並留 log

批次操作：選取多張一次作廢或延期（例如公休一週，把該期間到期的券全部延 7 天）。

## 8. 報表 `/admin/reports`

| 報表 | 內容 |
|---|---|
| 成本報表 | 依日/週/月，名目成本 vs 實際核銷成本，可匯出 CSV 給會計 |
| 獎項分析 | 每個獎項的中獎數、核銷數、核銷率、實際成本佔比 |
| 核銷率分析 | 各獎項真實核銷率，這個數字回頭餵給 §3.2 的成本試算 |
| 回訪分析 | 活動前後的回訪間隔對比 |
| 時段分析 | 發放與核銷的時段分佈 |

**成本報表要區分兩個數字：**

- **名目成本**：所有發出去的券的面額總和（潛在負債）
- **實際成本**：已核銷券的成本總和（真正花掉的錢）

跟會計對帳看實際成本，評估活動效益看名目成本。

## 9. 設定 `/admin/settings`

### 9.1 品牌

店名、Logo、主色。抽獎頁的視覺跟著這裡走。

### 9.2 活動總開關

```
活動狀態     (•) 進行中   ( ) 暫停

暫停時，客人掃 QR 會看到：
[ 活動暫停中，造成不便敬請見諒 ]

活動期間     [2026-08-01] 到 [        ]   留空 = 無限期
```

**一鍵暫停是必要的煞車。**成本失控、獎品缺貨、系統出問題時要能立刻停。暫停時已發出的券**仍然可以核銷**，只是不能再抽新的。這符合消保法要求。

### 9.3 活動規則

| 設定 | 預設 | 說明 |
|---|---|---|
| 券預設有效天數 | 21 | 獎項可個別覆寫 |
| 每次消費限用券數 | 1 | 防止一次用光一疊券 |
| 紙卡序號有效天數 | 90 | 印出來的卡多久後失效 |
| 動態 QR 存活秒數 | 60 | |
| 抽完到登入的領取時限 | 30 分鐘 | 超過未登入視為放棄 |
| 可否與其他優惠併用 | 否 | |

### 9.4 成本煞車

```
每月成本上限   [ 10000 ] 元    ( ) 不設限

達到上限時     (•) 只通知我
               ( ) 自動暫停活動

目前本月累計   NT$ 6,240 (62%)
```

我建議先選「只通知我」。自動暫停會讓客人在店裡掃碼卻抽不了，體驗很差，寧可你收到通知後自己決定怎麼處理。

### 9.5 保底機制

```
[✓] 啟用保底
    同一會員連續 [ 20 ] 次抽到最低價值獎項時，
    下一次強制給中等以上獎項
```

熟客一週來三次，連續抽到加麵券會覺得被耍。保底成本增加極小但體感差很多。

### 9.6 活動辦法

富文本編輯器，內容直接顯示在 `/rules` 頁。

**機率表由系統自動產生插入**，不要讓你手打。公平交易法要求公告機率必須真實，手打會有寫錯或忘記同步的風險。系統自動從 `prizes` 撈當前設定產生表格。

## 10. 技術實作要點

### 10.1 設定的讀取與快取

`settings` 是單列表，每次抽獎都要讀。用 Next.js `unstable_cache` 快取 60 秒，後台儲存時 `revalidateTag('settings')` 立即失效。

不要每次請求都打 DB，也不要快取太久導致「改完沒生效」的困惑。60 秒是平衡點，後台儲存後主動失效讓體感是即時的。

### 10.2 機率的即時試算放前端

`/admin/prizes` 的權重調整、百分比換算、成本試算，全部在前端即時算，不打 API。只有按儲存才寫 DB。這樣調整體驗才流暢。

但**抽獎本身的機率計算一定在後端**，兩者不衝突。前端算的只是給你看的預覽。

### 10.3 儲存時的原子性

獎項是一起儲存的（改一個權重會影響所有百分比），用 transaction 一次寫入全部異動，並在同一個 transaction 寫 `prize_change_log`。

### 10.4 後台不需要即時

除了儀表板，後台其他頁面都可以用 Server Component 直接查 DB，不用做即時更新。儀表板加一個手動重整鍵就夠，不用 WebSocket。

### 10.5 手機可用

你很可能在店裡用手機看後台。至少儀表板、券管理、序號啟用這三個要能在手機上操作。獎項編輯跟報表可以只做桌機版。
